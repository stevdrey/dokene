# Issue #246: Database outage fails fast with 503 and Retry-After

## Change
While PostgreSQL was down, data endpoints waited for Hikari's default 30 s `connectionTimeout` and then answered
Spring's generic JSON `500`. That was found by QA suite #123, RES-09.

The backend now:
- bounds the runtime pool wait (`DOKENE_DB_CONNECTION_TIMEOUT_MS`, default `3000`);
- answers a database outage with an **empty `503` and `Retry-After`** (`DOKENE_DB_UNAVAILABLE_RETRY_AFTER`, default
  `5s`).

The mapping runs at two boundaries:
- `AuditRequestFilter`, for failures inside the security filter chain, such as tenant membership resolution;
- `DatabaseUnavailableExceptionHandler`, for failures inside MVC.

Only the class of the connection-level failure is logged. See
[ADR 0029](../adr/0029-database-outage-http-semantics.md).

## Evidence
Code under test is the branch of this PR on top of `main` 50520d3, built into the local Compose stack with
`docker compose up -d --build`. I confirmed that the backend jar contains the `database` classes and the new
`application.yml` keys, and that the container received both new environment variables with their defaults. All data
is synthetic: the QA seed tenant and operator, plus one customer name generated by the script.

### Automated, backend
Run from `backend/` with JDK 26:
- `./gradlew check` passed: 2151 tests, 0 failures, 0 errors, 0 skipped.
- New tests:
  - `DatabaseUnavailabilityTest` covers the classification cases, the `Retry-After` rounding, the MVC `503`, and the
    MVC `500` for a transaction that could not start for a reason other than the connection.
  - `AuditRequestFilterTest` gains a filter-level outage case: `503`, `Retry-After`, `X-Request-Id`, empty body.
  - `DatabaseOutageIntegrationTest` runs against Testcontainers PostgreSQL over the real filter and security stack.
    It holds the only pooled connection so that every borrow times out. `GET`/`POST /api/customers` and
    `GET /api/follow-up-queue` answer an empty `503` with `Retry-After` in about 250 ms. The log has no pool or driver
    text, and the same caller gets `200` once the connection is released.
  - `ModuleDependencyArchitectureTest` keeps the `database` package independent of the other modules, except
    `ratelimit`.

### Manual, local Compose stack
This retest repeats the RES-09 reproduction with PostgreSQL really stopped. The script is
`issue-246-evidence/res09-retest.sh`, adapted from suite #123's `res09b.sh`. It needs the local QA login helper,
which is not versioned. The full output is in `issue-246-evidence/outputs.txt`.

Procedure:
1. Log in as the seed operator and call `GET /api/customers` (baseline `200`).
2. Run `docker compose stop postgres`.
3. Call the data endpoints with the same session.
4. Inspect the backend log for the outage window.
5. Run `docker compose start postgres`, then repeat the call with the same session.

| Call during the outage | Before (suite #123, `7069914`) | This branch |
|---|---|---|
| `GET /api/customers` (1st) | `500` JSON after 30 ms | empty `503`, `Retry-After: 5`, after 3041 ms |
| `GET /api/customers` (2nd) | not measured | empty `503`, `Retry-After: 5`, after 3029 ms |
| `GET /api/follow-up-queue` | `500` JSON after 30 020 ms | empty `503`, `Retry-After: 5`, after 3032 ms |
| `POST /api/customers` | `500` after 30 036 ms | empty `503`, `Retry-After: 5`, after 3027 ms |

Every `503` keeps the server-generated `X-Request-Id`.

Result: **PASS=27 FAIL=0**.
- **Backend log during the outage:**
  - one `Database unavailable at the HTTP boundary: exceptionClass=org.postgresql.util.PSQLException` line per
    request, each with its own correlation id;
  - no JDBC URL, host, user, password, stack trace or `500`.

  This is the real driver path (SQLState class `08`), not the pool-exhaustion path that the integration test uses.
- **Backend:** kept running.
- **Recovery:** after `docker compose start postgres`, the same session answered `200` with no backend restart (first
  call 1442 ms).
- **Writes:** the `POST` refused during the outage left no row.

## Observations
- Hikari logs its own `WARN ... Failed to validate connection org.postgresql.jdbc.PgConnection@… (This connection has
  been closed.)` lines while it discards dead pooled connections. They existed before this change and carry no host,
  credential or SQL text.
- An audit write that fails because of the outage keeps the ADR 0006 audit `503`, without `Retry-After`. This is out of
  scope by design (ADR 0029 §5).
