# Issue #246: Database outage fails fast with 503 and Retry-After

## Change
While PostgreSQL was down, data endpoints waited for Hikari's default 30 s `connectionTimeout` and then answered
Spring's generic JSON `500`. That was found by QA suite #123, RES-09.

The backend now answers a database outage with an **empty `503` and `Retry-After`**
(`DOKENE_DB_UNAVAILABLE_RETRY_AFTER`, default `5s`) instead of a generic `500`. It bounds every way a request can wait
on the database:
- **Pool wait:** `DOKENE_DB_CONNECTION_TIMEOUT_MS`, default `3000`. Startup refuses less than `500`.
- **Liveness check of an idle pooled connection:** 1000 ms, capped at half the pool wait.
- **One blocking read of a statement in flight:** a hard ceiling, `DOKENE_DB_SOCKET_TIMEOUT`, default `30s`.
- **Server-side `statement_timeout`:** `DOKENE_DB_STATEMENT_TIMEOUT`, default `25s`. It must be shorter than the
  socket ceiling, which startup checks. A statement or lock wait that is merely long is therefore cancelled as `57014`,
  is not reported as an outage, and keeps its connection.

A failure counts as an outage when its cause chain holds a lost connection:
- the pool timeout;
- SQLState class `08`;
- PostgreSQL's `57P01`, `57P02` or `57P03`.

The mapping runs at one boundary, `AuditRequestFilter`. It covers two kinds of failure:
- failures inside the security filter chain, such as tenant membership resolution;
- MVC failures that no advice resolves.

It checks the whole cause chain, so it needs no list of exception types. Its response reset keeps:
- the BFF security headers;
- CORS and `Vary`;
- `X-Request-Id`.

An audit write lost to the outage also carries `Retry-After`.

`Retry-After` is exposed to cross-origin clients. Only the class of the connection-level failure is logged. See
[ADR 0029](../adr/0029-database-outage-http-semantics.md).

## Evidence
Code under test is commit `0ec940d` of this PR, on top of `main` 50520d3. It was built into the local Compose stack
with `docker compose up -d --build`. Before testing I checked that:
- the backend jar contains `DatabaseUnavailability` and no longer contains the removed MVC advice;
- the container received `DOKENE_DB_CONNECTION_TIMEOUT_MS=3000`, `DOKENE_DB_UNAVAILABLE_RETRY_AFTER=5s`,
  `DOKENE_DB_SOCKET_TIMEOUT=30s`, `DOKENE_DB_STATEMENT_TIMEOUT=25s` and
  `DOKENE_CORS_ALLOWED_ORIGINS=http://localhost:5173`.

All data is synthetic: the QA seed tenant and operator, plus one customer name generated by the script.

### Automated, backend
Run from `backend/` with JDK 26:
- `./gradlew check` passed: 2167 tests, 0 failures, 0 errors, 0 skipped.
- **`DatabaseUnavailabilityTest`** covers:
  - classification: pool timeout, wrapped JPA failures, SQLState `08`, `57P01`/`57P02`/`57P03` but not `57014`, the
    JdbcTemplate translations of `08006`/`57P01` (outage) and `53100` (not an outage), cyclic causes;
  - `Retry-After` rounding;
  - class-only logging.
- **`AuditRequestFilterTest`** covers the filter-level outage `503`:
  - `Retry-After` and `X-Request-Id`;
  - CORS, `Vary`, CSP, nosniff and cache-control headers kept;
  - `ETag` and arbitrary headers dropped;
  - MVC outages that no advice resolves (JPA transaction begin, JdbcTemplate `08006` and `57P01`) reach the filter as
    an empty retryable `503`;
  - a full disk (`53100`) keeps the default handling;
  - an audit write lost to the outage gets `Retry-After` at both the filter and `AuditExceptionHandler`, while other
    audit failures do not;
  - a cyclic cause chain is rethrown instead of looping.
- **`TransactionalAuditRecorderOutboundSwitchTest`** checks that a lost connection flags the
  `AuditPersistenceException` and any other failure does not, still without a cause.
- **`DatabaseOutageIntegrationTest`** runs against Testcontainers PostgreSQL over the real filter and security stack.
  - **Pool wait:** a 1000 ms pool wait whose only connection is held by the test. `GET`/`POST /api/customers`,
    `GET /api/follow-up-queue` and a cross-origin `GET` answer an empty `503` with `Retry-After` in about 1 s. Each
    carries the configured BFF security headers, and the cross-origin one also carries `Access-Control-Allow-Origin`
    and `Retry-After` in `Access-Control-Expose-Headers`. The log has no pool or driver text, and the same caller gets
    `200` once the connection is released.
  - **Healthy database:** with a 300 ms `statement_timeout`, `SELECT pg_sleep(2)` is cancelled with `57014`, which is
    not classified as an outage, and the same connection stays usable.
  - **Bound settings:** it asserts `socketTimeout=30`, the `statement_timeout` option and the capped 500 ms validation
    timeout.
- **`DatabaseBlackholeIntegrationTest`** runs on a PostgreSQL container of its own. It pauses the container, a
  blackhole with no TCP reset, after Hikari's alive-bypass window. The stale idle connection fails validation and the
  request answers `503` in under 2.5 s, then recovers. No other integration class shares that container.
- **`TenantPersistenceConfigurationTest`** covers:
  - the validation-timeout cap;
  - the startup refusal of a pool wait below 500 ms and of a `statement-timeout` that is not shorter than
    `socket-timeout`;
  - the driver properties that are applied.
- **`ModuleDependencyArchitectureTest`** keeps the `database` package independent of the other modules, except
  `ratelimit`.

### Manual, local Compose stack
This retest repeats the RES-09 reproduction with PostgreSQL really stopped. The script is
`issue-246-evidence/res09-retest.sh`, adapted from suite #123's `res09b.sh`. It needs the local QA login helper, which
is not versioned. Its outputs are in `issue-246-evidence/outputs.txt`.

Procedure:
1. Log in as the seed operator and call `GET /api/customers` (baseline `200`).
2. Run `docker compose stop postgres`.
3. Call the data endpoints with the same session, one of them cross-origin from the configured SPA origin.
4. Inspect the backend log for the outage window.
5. Run `docker compose start postgres`, then repeat the call with the same session.

| Call during the outage | Before (suite #123, `7069914`) | This branch (run 1) |
|---|---|---|
| `GET /api/customers` (1st) | `500` JSON after 30 ms | empty `503`, `Retry-After: 5`, after 3048 ms |
| `GET /api/customers` (2nd) | not measured | empty `503`, `Retry-After: 5`, after 3021 ms |
| `GET /api/follow-up-queue` | `500` JSON after 30 020 ms | empty `503`, `Retry-After: 5`, after 3029 ms |
| `GET /api/customers` (cross-origin) | not measured | empty `503`, `Retry-After: 5`, after 3042 ms |
| `POST /api/customers` | `500` after 30 036 ms | empty `503`, `Retry-After: 5`, after 3025 ms |

Run 1 result: **PASS=40 FAIL=0**.
- **Every `503`** keeps the server-generated `X-Request-Id`.
- **The cross-origin `503`** also carries:
  - `Access-Control-Allow-Origin: http://localhost:5173` and `Access-Control-Expose-Headers: ETag, X-Request-Id, Retry-After`;
  - the BFF security headers: CSP, Permissions-Policy, nosniff, `X-Frame-Options: DENY`, Referrer-Policy and
    `Cache-Control: no-store`.
- **Backend log:**
  - one `Database unavailable at the HTTP boundary: exceptionClass=org.postgresql.util.PSQLException` line per
    request, class only, each with its own correlation id;
  - no JDBC URL, host, user, password or SQL text, and no `500`.
- **Backend:** kept running.
- **Recovery:** after `docker compose start postgres`, the same session answered `200` with no backend restart.
- **Writes:** the `POST` refused during the outage left no row.

Run 2 used the earlier build `3867acc`. It went through the same filter-boundary path, which `0ec940d` does not
change. PostgreSQL ended a pooled connection with `57P01` (`admin_shutdown`) while it was in use.
The first call answered an empty `503` with `Retry-After` in **30 ms**. This is the in-flight shutdown path, the same
call that suite #123 measured as a `500` in 30 ms. HikariCP logged `marked as broken because of SQLSTATE(57P01)`.

That run's only FAIL came from an earlier revision of the script's log check. It counted HikariCP's own stack frames
for that warning as a leak. The check has since been split: boundary lines must be class-only, and no host,
credential or SQL text may appear anywhere. Both pass for that window.

## Observations
- HikariCP logs its own warnings while it discards dead pooled connections. Both existed before #246, sit outside the
  HTTP boundary, and carry no host, credential or SQL text.
  - `Failed to validate connection ... (This connection has been closed.)`.
  - On `57P01`, `marked as broken` with the driver exception and its stack frames. The only message is
    `FATAL: terminating connection due to administrator command`.
- `DispatchRecoveryProcessor` logs its scheduled run failing during the outage as
  `errorType=CannotGetJdbcConnectionException`, class only.
- Audit persistence failures follow ADR 0029 §5:
  - An audit write that fails because of the database outage answers the empty ADR 0006 audit `503` **with**
    `Retry-After`. `AuditPersistenceException.databaseUnavailable()` carries that as a boolean, still with no cause or
    text.
  - Any other audit persistence failure keeps the empty `503` **without** `Retry-After`.
