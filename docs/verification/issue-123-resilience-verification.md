# Issue 123 verification: live AI failures, bounded retry, stale state and dependency recovery

Campaign: #118. Suite: #123. Tested on `main` @ `7069914` (includes #187-#190 and #195-#197 fixes), local Docker stack, synthetic data only. The suite starts with a live OpenAI success (`gpt-6-luna`), explores faults, and ends with the original configuration restored and a live success again (RES-11).

**Methodology and sources.** Genuine OpenAI responses: the baselines before and after, RES-01 cases 4b (upper-case provider name), 6 (invalid key, HTTP 401) and 7 (unknown model, HTTP 404), and the live recoveries in RES-07 and RES-11. **Everything else about the provider is injected** by the local fault-injection stub of suite #121 (extended here with Retry-After headers, refusal output, success-only latency) reached through `DOKENE_AI_OPENAI_BASE_URL`, plus a connection-refused and a blackholed address for the offline cases; each case below says which. Configuration per case is a compose override (environment only), removed afterwards. About 12 live OpenAI calls were made in this suite.

**Verdict for suite #123: PASS with one Low finding (#246).** The retry budget, the authority rechecks, the drift handling, the idempotency controls and the dependency recovery behave as documented.

## Observations (not filed)

- The `model` meter tag takes the value returned by the provider response (`stub` in the injected runs, `gpt-6-luna` live); a provider returning many distinct snapshot ids would grow the tag cardinality.
- If the metrics endpoint is ever exposed, any authenticated OPERATOR session can read it (VIEWER is denied); the BFF applies no finer authorization to actuator paths. It is not exposed by default.
- The deterministic queue and manual follow-ups stayed available in every AI failure case; the AI audit uses `FAILED/REFUSED` for a refusal content part and `SUCCESS` only for explicit valid no-recommendation/no-draft outcomes, as in ADR 0019.

## Limitations

- Provider faults other than the live 401/404 are injected; genuine OpenAI 429, 5xx and refusals were not provoked (they cannot be forced, and would cost real calls).
- Network throttling was emulated with injected latency and unreachable addresses rather than traffic shaping.
- Retry timing is measured from the stub log (server-side timestamps), not from OpenAI.
- Harness incidents: stub handler threads outlive a client timeout and consume the next case's fault count; the restart of the backend without the compose override returned it to the live provider, which the report labels where it affected a case (RES-07 recoveries).
