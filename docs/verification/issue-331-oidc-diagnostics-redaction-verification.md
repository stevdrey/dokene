# Issue #331 Sensitive values in OIDC verification diagnostics: verification record

Status: single PR, part of epic [#305](https://github.com/stevdrey/dokene/issues/305). It closes [#331](https://github.com/stevdrey/dokene/issues/331): a failure message of the local OIDC verification script `scripts/verify-keycloak-bff-e2e.sh` could print a configured secret or another value of the login flow. The rule is part of [security invariant 35](../security/security-invariants.md).

This record is sanitized. Every value used in the checks below was synthetic: random per run, generated by the test or for a throwaway container, and discarded with it. No credential, token, authorization code, OAuth state, CSRF token, session id or output holding one is reproduced here. It gives outcomes, counts and settings only.

## Recheck before the change

The Issue analysed revision `a3288485`. Its two locations had already changed on `main`: issue 382 moved the test password to curl's stdin, and issue 327 replaced the regular expression secret search with literal matching (`scripts/lib/secret-match.sh`), named the client secret `<OIDC client secret>` in its two leak checks, and showed the post-login redirect as its origin only.

On `11c5917d`, seven other failure paths still printed a raw value from the flow:

| Failure path | What the message printed |
| --- | --- |
| Login start redirect not at the realm authorization endpoint, or without S256 PKCE | the whole authorization URL: OAuth `state`, `nonce`, PKCE challenge |
| Keycloak not refusing a request without PKCE | the whole `Location`, which can hold an authorization code |
| Credentials submit not redirected to the BFF callback | the whole `Location`, which can hold an authorization code |
| Invalid session contract | the whole session body: CSRF token and identity id |
| Logout cookie without expiry | the whole `Set-Cookie` header, which can hold the session id |
| Session body that is not JSON | nothing: `jq` ended the script under `errexit` with no `FAILED` line |

The script also read the client secret after loading `.env` with `set -a`, so `.env` overwrote a value exported by the caller. docker compose gives the exported value precedence, so the leak checks could search for a secret the stack did not use. Nothing checked that the value was the one in effect.

## Change

| Part | Before | After |
| --- | --- | --- |
| Failure messages | raw URL, session body or cookie header on the paths above | the URL's origin only (`redact_url`), field states (`authenticated not true, identityId present, csrfToken missing; body withheld`), or a fixed sentence (`header withheld`) |
| Leak checks | a loop over the names and the secret, with a lookup to pick the label | `leaked_label`: literal search (`contains_literal`) for each OAuth parameter name, then the secret; it prints only a fixed label (`access_token`, …, `<OIDC client secret>`), never text from the response |
| Client secret resolution | `.env` overwrote an exported value | the caller's exported value first, then `.env`, then the oidc-bridge name, as docker compose resolves it |
| New step 3 | none | a token request with an unusable code and the configured secret on curl's stdin. The right secret gets 400 `invalid_grant`; a wrong one gets 401, and the script stops with `Keycloak refused the configured <OIDC client secret>` before any leak check. No code is redeemed and no token issued; only an error code of plain letters is printed |
| Step 3 error code | any value of plain lowercase letters and `_` from the response's `error` field | only a registered OAuth token error code (RFC 6749 section 5.2), printed as the script's own copy; any other value is `<unrecognized error>`, so a response that reflects the secret in that field does not print it. The HTTP status is printed only as three digits |
| Step 3 classification | any `unauthorized_client` reported as a wrong secret | a wrong secret is HTTP 401 or `invalid_client`; a 400 `unauthorized_client` is reported as a client configuration problem, not the secret |
| Redirect host | printed in full unless it held the client secret | withheld as `<host withheld: it has a label of 32 or more characters>` when a host label is 32 characters or longer, the length of a code, state, nonce, CSRF token or session id |
| Session parsing | `jq` on a shell variable, under `errexit` | the body must first be exactly one JSON object (`jq -s`), else `FAILED (Invalid session contract: response is not a single JSON object; body withheld)`. A non-JSON body, a valid object followed by trailing content, or two JSON values all fail there; `jq` cannot print fields from a partly parsed body. One `jq` then reports field states only: `authenticated` must be the boolean `true`, `identityId` and `csrfToken` non-empty strings (review follow-ups) |

The script now has 12 steps.

## Limitations

- The full script was not run against a real BFF and Keycloak together. The flow was checked against the stub, and the one new request to a real service (step 3) against a throwaway Keycloak. A live stack run needs `./scripts/dev-env.sh up`; the existing QA stack on this machine was not touched.
- The script shows a URL's origin, so a failure still names the host it was sent to. That is the diagnostic the issue 327 review asked to keep, A well-formed redirect's origin carries no token, and a host label of 32 or more characters, the length of any value of the flow, is withheld; a shorter value placed in the host would still be shown.
- Step 3 proves Keycloak accepts the configured secret. That this is the same value the BFF uses follows from the BFF completing the code exchange in step 7, which Keycloak only allows with the right client secret.
