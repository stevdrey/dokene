# Issue #330 Sensitive request data in proxy logs: verification record

Status: single PR, part of epic [#305](https://github.com/stevdrey/dokene/issues/305). It closes [#330](https://github.com/stevdrey/dokene/issues/330): the nginx edge wrote the raw request line, query string included, to its access log on every request and to its error log on every failed one, so the Meta webhook verify token, OAuth callback codes and customer search terms reached the proxy logs. The rule is [security invariant 41](../security/security-invariants.md); operator guidance, including rotation, is in [`infra/docker/README.md`](../../infra/docker/README.md#edge-logs).

This record is sanitized. Every value sent was a random marker generated by the test run, never a real credential, and no marker, token, code or log excerpt holding one is reproduced here. It gives outcomes, counts and settings only.

## Recheck before the change

On `358f8ea4`, the frontend image was run on a test network without a backend, and two requests were sent: a webhook verification `GET` with a synthetic verify token, and a customer search with a synthetic phone number in its query string.

| Stream | Lines holding a marker | Where |
| --- | --- | --- |
| stdout (access log, base image `main` format) | 2 of 2 requests | the `"$request"` field, query string included |
| stderr (error log, `notice`) | 2 of 2 requests | the `request: "GET …?…"` context of `backend could not be resolved` |

The access log leaked on every request, success included; the error log leaked on every request scoped failure. The new smoke test was written before the change and failed 16 of its 21 checks against `358f8ea4`.

## Change

| Part | Before | After |
| --- | --- | --- |
| Access log | the base image's `main` format at http level: raw request line, raw `Referer`, `$remote_user`, user agent, `X-Forwarded-For` | one `access_log /dev/stdout redacted` in the server block, which replaces the http level one: client address, time, method, path up to its first `?`, `;`, `%3F` or `%3B`, protocol, status, bytes, request time, `upstream=<address>/<status>`, upstream response time, `Referer` without userinfo, cut at its first `?`, `#`, `;`, `%3F`, `%3B` or `%23`. No client supplied header |
| Error log | `notice` from the base image for every location, `error` on `/webhooks` | `error_log /dev/null` in the server block and none in any location, so no request scoped line is written on any route. Process level lines still reach stderr |
| Diagnostics | the error line's reason | the access log status and upstream fields (table in `infra/docker/README.md`) |

The first field of the access log is still the client address, which the login rate limit smoke test and the trusted proxy instructions read.

## Review findings

A review of `9519f7eb` raised eight points; seven are fixed:

- The logged path kept `;jsessionid=` path parameters and text after an encoded `?`. It is now cut at the first `?`, `;`, `%3F` or `%3B`.
- The logged `Referer` kept URL userinfo. It is now dropped.
- The format logged the client supplied user agent and `X-Forwarded-For`. Both are gone; the restored client address stays the first field.
- `error_log /dev/null` covered the whole server, so static route errors were hidden too. Narrowing it to the proxied locations was tried and refused by the independent re-verification: a static route also fails with the query string in its error line (a body over the cap, an invalid chunked body). The server level setting stays, and the smoke test now sends an over-cap body to a static route.
- The format check was a short deny list. It is now an allowlist of the variables the format may name.
- The static checks read `nginx.conf` only. They now read every snippet too.
- Fixed 11 second waits for the resolver cache became a poll on a probe request.
- The upstream assertion matched any `upstream=-…` prefix. It now matches the whole `upstream=-/-` token.

A later PR review comment found that the `Referer` still kept path parameters, so `;jsessionid=<id>` in the page a request came from reached the access log; a probe on `2f46f36c` reproduced it with both `;` and `%3B`. The `Referer` is now cut the same way as the path, at its first `?`, `#`, `;`, `%3F`, `%3B` or `%23`, and a scheme relative `Referer` (`//user:pass@host/`) also loses its userinfo. Both search Referers in the smoke test now carry a session id marker; against `2f46f36c` it fails 7 checks.

## Exposure and rotation

Exposure was confirmed for images built before this change, in their own logs: the verify token on every webhook verification, and OAuth codes and search terms on every request. In this local stack those logs are Docker's log files for the frontend container and are removed with it; nothing here ships them elsewhere. No real token was in any log read for this record. Where logs of an older image were kept or shipped, `infra/docker/README.md` says what to do: rotate the WhatsApp webhook verify token in the integration secret source and in the Meta app together, delete or restrict the logs, and treat search terms in them as personal data. Callback codes are single use and short lived and need no rotation.

## Limitations

- A manual probe of the review fix sent eight malformed requests with a marker in a webhook or search query string (a bad header line, no `Host`, a 20 KB header, `Transfer-Encoding` with `Content-Length`, two `Host` headers, `HTTP/9.9`, a non-numeric `Content-Length`, a truncated header); nginx answered `400` or `505` and wrote no marker to stdout or stderr.
- A `Referer` with a `/` inside its password keeps part of its userinfo in the log. Browsers never send userinfo in a `Referer`. A manual probe of the Referer fix confirmed that a scheme relative `//user:pass@host/x`, an upper case scheme with an IPv6 host and a path parameter, a relative path with `;jsessionid=`, and `%23` and `%3b` in a path are all logged without the marker.
- Only the shipped edge configuration is covered. A deployment that adds an `error_log` to a location, mounts another nginx configuration, or puts another proxy or tunnel in front of this edge must apply the same rule there; this test cannot see those logs.
- An edge failure now leaves only its status and upstream fields; the reason text nginx would have written is gone. This is the intended trade off.
- Timeouts (`504`) and a full `/tmp` (`500`) were not provoked; they write through the same error log, which writes nothing.
