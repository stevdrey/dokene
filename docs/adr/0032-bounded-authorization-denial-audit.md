# ADR 0032: Bounded Authorization Denial Audit

## Status

Accepted. Issue: [#310](https://github.com/stevdrey/dokene/issues/310), finding L1 of the [security audit of 2026-11-02](../security/security-audit-2026-11-02.md) (epic [#305](https://github.com/stevdrey/dokene/issues/305)). Amends the rule of [ADR 0005](0005-tenant-aware-authorization.md) and [ADR 0006](0006-durable-append-only-audit.md) that every enforced denial writes one audit row.

## Context

Every enforced authorization denial wrote one `AUTHORIZATION_DENIED` row in its own `REQUIRES_NEW` transaction. Nothing limited how often one caller could be denied, and `audit_events` is never purged. The audit showed that one signed in user with no membership added 1,000 rows with 1,000 requests carrying a foreign `X-Tenant-Id`. The table could grow without limit, real denials could be buried in noise, and each denial held a pooled connection.

The first denials of a kind are what an investigation needs. The thousandth identical denial adds only its time and correlation id. A bound must keep the first ones itemized, keep a visible count of the rest, and never change whether a request is refused.

## Decision

1. **One place.** The bound lives in `TransactionalAuditRecorder.authorizationDenied`, the only method that writes denial rows. Authorization code is not changed. The recorder builds the event first, exactly as before, so a missing correlation scope or an invalid event fails the same way and never reaches the budget.
2. **Key budget.** A *key* is (identity, tenant or none, denial reason, permission or none). The first `rows-per-key` denials of a key inside one window (default 10 in 15 minutes) each write their row as before. Later denials of that key in that window write no row and are counted in memory. The tenant is part of the key, so a tenant's rows and counts reflect only denials in that tenant.
3. **Identity ceiling.** One identity writes at most `rows-per-identity` rows per window (default 60) across all its keys, with and without a tenant. A denial refused by the ceiling is counted under its own key.
4. **Fixed windows.** A window opens at the first denial of its key (or identity) and ends one window length later. The first denial at or after the end opens a new window with a full budget. A unit spent on a row stays spent when the write then fails, so a failing database never hands out extra attempts.
5. **Whose budget.** The identity is the one in the bound tenant context. Without a context it is the identity the caller passes through the new `AuditRecorder.authorizationDenied(permission, reason, identityId)`; `TenantContextRequestFilter`, `TenantController.getWorkspace` and `WorkspaceProvisioningService` pass it. A denial with no context and no identity is charged to one slot shared by all such callers. The identity only picks the budget. It is never stored on an unattributed row (ADR 0006).
6. **Summary row.** A sweep (default every minute) appends one `AUTHORIZATION_DENIALS_SUPPRESSED` row for each ended window with a count above zero. The row carries the count in the new column `suppressed_count`, the key's permission and reason, the correlation id of the first suppressed denial and, for a tenant key, the tenant, actor and membership of that denial. It is written under that tenant context with an audit capability minted at write time, so it is still written after the member was revoked. Its row id is fixed when the count first goes above zero, so a retry can never produce a second row: a primary key conflict means it was already written.
7. **Sweep limits and failure.** One run writes at most 500 rows, oldest first. A write that fails because the database is unavailable stops the run and keeps every count for the next run. A write the database rejects for another reason is logged at `ERROR`, counted and dropped. A graceful shutdown writes the counts of ended and still open windows, and of denials counted while it was writing. It starts no write after 10 seconds; a write already running then may still take up to its own transaction timeout. Its last step looks at the tracker once more and logs the windows and denials it could not write.
8. **Capacity.** The tracker holds at most `max-tracked-keys` windows (default 50,000), counting ended windows whose count is not written yet. While it is full, a denial of a key it does not track writes no row and is added to an overflow count. Each sweep writes that count first, as one summary row with no attribution, no permission and no reason. The ceiling per identity is tracked apart from the windows and is not counted in the capacity: at most one small entry per identity seen in the last window.
9. **Signals.** Every suppressed denial increments `dokene.audit.denials.suppressed`, tagged with the denial's `reason` and the `cause` (`KEY_BUDGET`, `IDENTITY_CEILING`, `TRACKER_FULL`). The first suppressed denial of a key window logs one `WARN` line with the identity UUID, reason, permission and cause. The first overflow after each sweep logs one `ERROR` line. Summary writes are counted in `dokene.audit.denials.summaries` by `result`, and the gauge `dokene.audit.denials.tracked.keys` reports the tracker size. No tag or log line contains client supplied text, a tenant id from a request header or a foreign resource id.
10. **Fail closed.** The outcome of an authorization check never depends on the budget. If the budget throws, the row is written as before and the error is logged with the exception class only.
11. **Database.** Migration V40 adds the nullable column, the constraint `ck_audit_suppressed_count` (a count exists exactly on the summary type and is at least 1) and one branch of `ck_audit_shape` that admits three summary shapes: attributed (tenant, actor, membership and a tenant reason), unattributed (no tenant, `NO_TENANT_CONTEXT`) and tracker full (no tenant, no reason, no permission). The column and both constraints are added in one `ALTER TABLE`, so PostgreSQL checks the existing rows in a single scan. `dokene.append_audit_event` gains one trailing parameter with a default. Without a capability it accepts only `NO_TENANT_CONTEXT` denials and the two summary shapes without a tenant. The runtime role still cannot insert, update or delete rows directly.
12. **Configuration.** `dokene.audit.denial-limit.*` (`rows-per-key`, `rows-per-identity`, `window`, `max-tracked-keys`, `sweep-interval`) is validated at startup, and the application refuses to start on a value outside its range. No setting turns the bound off.

Alternatives rejected: a token bucket in front of the recorder that drops denials without a count (suppression would be invisible); a count column updated in place on the first row (audit rows are append only); a database table of counters (every denial would still cost a write and a pooled connection); a rate limit on the HTTP routes (it would not cover denials raised below the filter, and it would change what a caller sees).

## Consequences

- One identity can cause at most 60 denial rows per window and instance, plus one summary row per key it touched. The table still grows forever, only at a bounded rate; retention and purge stay undecided (ADR 0006).
- "Every denial has a row" is no longer true. Past the budget only a count survives, not each request's time and correlation id.
- A suppressed denial costs no audit write and no pooled connection for one. What the request did before it was refused is unchanged: the L1 flood still reads the membership of each foreign `X-Tenant-Id`.
- Migration V40 scans `audit_events` once while it holds an `ACCESS EXCLUSIVE` lock on the table. Audit writes of a running backend wait until the migration commits, and on a very large table a waiting denial inside budget can time out and answer `503`. V38 had the same cost. Should the table grow large before this is deployed, add the constraints `NOT VALID` and validate them in a later migration instead.
- A summary row arrives up to one window plus one sweep interval after the first suppressed denial, later when more than 500 are waiting.

Residual risks, accepted:

- **Per instance state.** The budget is held in memory. The real bound is the budget times the number of backend instances, and it resets on restart. During a rolling deployment an instance of the previous release still writes one row per denial.
- **Hard stop.** A crash loses the counts not yet written. So does a graceful shutdown for the counts it could not write before its deadline or during an outage (it logs their number), and for a denial counted after its last look at the tracker (not logged; the web server has stopped taking requests by then). The metric recorded them only if it was scraped.
- **Shared ceiling across tenants.** An identity that spends its 60 rows in one tenant gets only counts in its other tenants for the rest of that window.
- **Full tracker.** While the tracker is full, denials of untracked keys are counted but not itemized. An attacker with tens of thousands of accounts could cause that on purpose; the `ERROR` line and the `TRACKER_FULL` metric show it. The effect outlasts the burst: a window with a count keeps its place until its summary is written, and a sweep writes at most 500 per run. With the defaults a tracker filled once with 50,000 counted windows needs about 100 sweeps (about 100 minutes) to empty, and above about 7,500 new counted windows per 15 minutes the backlog does not shrink. Keys multiply by tenant, and nothing limits how many workspaces one identity allowed to provision may create, so where provisioning is open to everyone fewer accounts are needed.
- **Shared slot.** Denials with no tenant context and no identity share one budget. A caller able to cause such denials at will could use it up and leave other such callers only a count for one window. No HTTP route was found that lets a user do so (see the [verification record](../verification/issue-310-denial-audit-bound-verification.md)).
- **Outage visibility.** During a database outage a denial inside budget answers `503` ([ADR 0029](0029-database-outage-http-semantics.md)) while a suppressed one answers its normal refusal, so the status a caller sees can differ by budget state.
- **Dropped summaries.** A summary the database rejects is dropped after one `ERROR` line; only the log and the metric keep the count.
