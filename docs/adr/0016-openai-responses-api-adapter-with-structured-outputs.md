# ADR 0016: OpenAI Responses API Adapter with Structured Outputs

## Status

Accepted

## Context

Following the definition of structured recommendation contracts ([ADR 0015](0015-structured-next-best-action-recommendation-contracts.md)) and the provider-neutral `AiProvider` invocation port (Issue #90), Dokene requires its first concrete hosted-model adapter to generate Next Best Action recommendations.

Under [ADR 0004: AI Action Gate](0004-ai-action-gate.md) and the Dokene Security Model, external AI models are untrusted advisory components. Crucially:
1. Vendor SDKs must not leak into core application or domain modules.
2. Prompts, raw model outputs, and API credentials must never be logged or stored in plain application tables.
3. Provider failures must be normalized to application-owned categories (`AiFailureCategory`).
4. Automated CI must not depend on live external network access or real provider API keys.

## Decision

### 1. Official OpenAI Java SDK and Responses API

We adopt the official OpenAI Java SDK (`com.openai:openai-java:4.69.3`) and configure generation using the **Responses API** (`client.responses().create(...)`). The Responses API represents the modern generation interface in the official SDK, offering first-class support for developer instructions, structured outputs, and fine-grained request execution options.

### 2. Integration Boundary and Dependency Direction

The concrete adapter `OpenAiResponsesApiAdapter` is placed in the provider layer under `io.github.stevdrey.dokene.ai.provider.openai`, implementing the provider-neutral `AiProvider` port:

```text
followup.application
       │
       ▼
   ai.application (AiProvider interface)
       ▲
       │
ai.provider.openai (OpenAiResponsesApiAdapter)
       │
       ▼
com.openai (OpenAI Java SDK)
```

No types from `com.openai` or its dependencies are exposed to the `ai.application` or `followup` modules.

### 3. Strict Structured Outputs Integration

The adapter configures `ResponseCreateParams` with `ResponseTextConfig` and `ResponseFormatTextJsonSchemaConfig` using `strict: true` and the schema generated by `RecommendationJsonSchema.generateSchema()`.

Returned response payloads are extracted and deserialized directly into the application-owned `RecommendationOutcome` sealed hierarchy using `RecommendationJsonSchema.parseOutcome(...)`. If the model output violates schema invariants, fails validation, or contains unexpected properties, the adapter fails fast with `AiFailureCategory.INVALID_STRUCTURED_RESPONSE`.

### 4. Prompt Injection Defense and Trust Classification

The adapter preserves the structural separation established by `RecommendationContext`:
- **Developer Instructions**: A fixed system prompt defines the assistant's role and explicitly commands the model to ignore any system instructions, policy overrides, or commands embedded within customer-supplied text.
- **Context Delimitation**: Prompt inputs clearly separate `<trusted_facts>` (authoritative status, dates, cadence, and allowed action vocabulary) from `<untrusted_customer_data>` (display names, customer notes, and purchase descriptions).

### 5. Failure Normalization and Safe Diagnostics

All SDK and HTTP exceptions are mapped into application-controlled `AiFailureCategory` values:
- **`RateLimitException` (429)**: Mapped to `AiFailureCategory.THROTTLED`.
- **`InternalServerException` (5xx)**: Mapped to `AiFailureCategory.UNAVAILABLE`.
- **Client Errors (400, 401, 403, 404, 422)**: Mapped to `AiFailureCategory.REJECTED_REQUEST`.
- **I/O & Socket Timeouts**: Mapped to `AiFailureCategory.TIMEOUT`.
- **Schema Violations / Malformed JSON**: Mapped to `AiFailureCategory.INVALID_STRUCTURED_RESPONSE`.
- **Thread Interruption**: Mapped to `AiFailureCategory.CANCELLED`, restoring the thread's interrupt status.

Every mapped exception and response produces `AiInvocationMetadata` carrying diagnostic data only: provider ID (`openai`), sanitized model ID, provider request ID (validated against safe identifier patterns), latency, token usage (`AiTokenUsage`), and completion status. Exception messages and logs never include raw prompts, customer text, or API credentials.

### 6. Externalized Configuration and Secret Handling

Configuration is externalized through `OpenAiProviderProperties` (`@ConfigurationProperties(prefix = "dokene.ai.openai")`):
- `dokene.ai.provider`: Controls provider selection (`fake` for offline/testing, `openai` for production).
- `dokene.ai.openai.api-key`: Sourced from `DOKENE_AI_OPENAI_API_KEY`. Never committed or hardcoded.
- `dokene.ai.openai.model`: Configurable model name (default: `gpt-6-luna`), avoiding domain coupling to a single model.
- `dokene.ai.openai.base-url`: Sourced from `DOKENE_AI_OPENAI_BASE_URL` to support proxies or local gateways.
- `dokene.ai.openai.timeout`: Configurable timeout (default: `15s`).

A shared singleton `OpenAIClient` is reused across all requests.

### 7. Deterministic Test Strategy in CI

Contract and integration tests for the adapter utilize an in-process mock HTTP server (`com.sun.net.httpserver.HttpServer`) running on an ephemeral port. Normal CI builds run deterministically without external network egress or real API keys.

## Consequences

- **Provider Portability**: Core follow-up orchestration depends only on `AiProvider`; swapping or augmenting OpenAI with another provider requires no changes to business logic.
- **Zero-Secret & PII Hygiene**: Raw prompts, responses, customer PII, and credentials are completely absent from logs and exception messages.
- **Strict Deterministic Guardrails**: Model output remains purely advisory; successful schema deserialization does not bypass the deterministic AI Action Gate.
- **Safe CI Execution**: The adapter is thoroughly verified against success, refusals, malformed payloads, rate limits, timeouts, and cancellations without external network dependencies.
