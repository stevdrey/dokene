# ADR 0039: Bounded Follow-up Retries and Explicit Recovery

## Status

Accepted. Issue: [#461](https://github.com/stevdrey/dokene/issues/461) (Phase 4 A3), part of epic [#457](https://github.com/stevdrey/dokene/issues/457).

It builds on [ADR 0037](0037-durable-multi-instance-follow-up-work-claiming.md) (work ledger), whose states, fencing and open-item rule stay unchanged.

## Context

The work ledger (A2) records claims, retries and exhaustion but leaves three decisions open: how an attempt's failure is classified, when a retry runs, and what happens to an exhausted item. Follow-up work may lead to an external effect, such as a message reaching a provider. An attempt whose effect is uncertain must never be replayed blindly, and the Phase 3 send reconciliation ([ADR 0030](0030-verified-webhook-inbox-and-delivery-reconciliation.md)) remains the only way to settle a message whose send outcome is unknown. The scheduler (A4 [#463](https://github.com/stevdrey/dokene/issues/463)) and provider health monitoring (B1 [#469](https://github.com/stevdrey/dokene/issues/469), whose provider health state landed in [#471](https://github.com/stevdrey/dokene/issues/471) as [ADR 0038](0038-provider-health-gate.md)) are developed in parallel, so this decision defines the ports they plug into.

## Decision

1. **Classification.** A `FollowUpWorkHandler` (supplied by A4, later by Phase 5 dispatch) reports one `FollowUpWorkAttemptResult` per attempt:
   - `Completed`;
   - `Transient(PROCESSING_ERROR | DEPENDENCY_UNAVAILABLE)`: no external effect happened and a later attempt may succeed;
   - `Permanent(PROCESSING_ERROR | REJECTED)`: no external effect happened and retrying unchanged cannot succeed. `REJECTED` is a new safe category (V50);
   - `OutcomeUnknown`: an external effect may have happened.

   A handler that cannot prove that no external effect happened must report `OutcomeUnknown`. `FollowUpWorkProcessor` records any exception the handler throws, and a missing result, as `OutcomeUnknown`, never as a retryable failure. It logs only the exception class, never its message.
2. **Bounded retries.** `Transient` goes through `FollowUpWorkLedger.fail` with `retryAt = now + backoff(attempt)`. The backoff is `min(max-backoff, initial-backoff × 2^(attempt−1))` less a random share of at most `jitter` of it (`dokene.follow-up.retry.*`: initial 1 minute, from 1 second to 24 hours; max 30 minutes, up to 24 hours and never below the initial delay; jitter 0.2, from 0 to 1). A delay is never below 1 second, so a retry instant is never already past when the ledger records it. Attempts stay bounded by `dokene.follow-up.work.max-attempts` (ADR 0037). The ledger exhausts the item on its last attempt, and a safe exhaustion releases the customer. Once a handler reports `DEPENDENCY_UNAVAILABLE`, the batch's remaining claims are released the same way without being attempted. `FollowUpWorkLedger.fail` now refuses `REJECTED` as well as the unknown categories.
3. **Exhaustion without retry.** `Permanent` calls `requireRecovery(claim, failure)`, which exhausts the item at once and releases the customer. `OutcomeUnknown` calls `requireRecovery(claim, OUTCOME_UNKNOWN)`, which keeps the customer's open slot (ADR 0037 decision 2), so no newer follow-up starts for that customer until a member decides. A crash on the last attempt ends as `LEASE_EXPIRED` and is treated the same way.
4. **Provider health.** Before claiming, the processor reads the `FollowUpProviderHealth` port. B1 tracks provider health ([ADR 0038](0038-provider-health-gate.md), issue 471), but no adapter maps that state onto this port yet, so until one exists the processor sees `UNKNOWN`. `UNAVAILABLE` claims nothing, so no attempt is spent during an outage. `DEGRADED` and `UNKNOWN` claim one item as a probe. `UNKNOWN` also applies when no monitor is wired or the monitor fails. Health is a hint, never an authorization: the holder still re-checks every gate.
5. **Stale claims.** Claims of one batch are worked one after another, so the processor renews each claim's lease just before its handler starts and skips, as `stale`, a claim that expired or that another instance took over while it waited. The handler gets a `Lease`. It must renew the lease while it works and stop at once, with no external effect, when a renewal returns `false`. A stale claim's outcome records nothing (ADR 0037 decision 4). The processor counts it as `stale` and leaves the item to the newer holder. A renewal that throws before a handler starts means no handler ran and nothing external happened, so that claim and the rest of the batch are released as `DEPENDENCY_UNAVAILABLE`: retried after the backoff, or exhausted as a safe, requeueable failure, never as an unknown outcome. If even that release cannot be written, the claim waits for its lease to expire. A failed outcome write after a handler, or an `Error` a handler throws, releases the claims not yet handed to a handler the same way; an `Error` first records an unknown outcome for its own claim, then ends the run. Claims left to their lease this way are counted as `abandoned` in the run summary.
6. **Explicit, authorized, audited recovery.** `GET /api/follow-up-work/recovery?limit=1..100` (`FOLLOWUP_READ`) lists the tenant's exhausted, non-collapsed items, oldest finish first. Each item shows its ids, due date, state, last safe failure, whether its outcome is unknown, its attempts, its finish instant and its recovery count. `POST /api/follow-up-work/recovery/{candidateId}` (`FOLLOWUP_WRITE`) takes exactly `{"action":"REQUEUE"|"RESOLVE"}` and a strong `If-Match` on the recovery count:
   - `REQUEUE` makes the item `RETRY_DUE` now with a fresh attempt budget. V50's `attempt_base` records the attempts already used; the attempt number keeps growing, so the fencing identity stays monotonic. It is allowed only for a failure known to have had no external effect (`PROCESSING_ERROR`, `DEPENDENCY_UNAVAILABLE`, `REJECTED`), at most `dokene.follow-up.retry.max-requeues` times (default 3, up to 20, 0 disables it), and only while the customer has no other open work and no newer cycle that was already enqueued, finished or not (compared by the database's candidate `recorded_at`), so a superseded cycle is never worked again.
   - `RESOLVE` records the item as `COMPLETED` without another attempt, keeps its last failure for history, and releases the customer. It is the only recovery for an unknown outcome. The member settles the message itself through the Phase 3 reconciliation; recovery never sends, replays or touches a message.

   Each applied decision runs in the member's tenant context under forced RLS and records `FOLLOW_UP_WORK_REQUEUED` or `FOLLOW_UP_WORK_RESOLVED` (customer target, no metadata) in the same transaction, so a failed audit write rolls the decision back. A refused decision returns `409` with one of `STALE_VERSION`, `NOT_EXHAUSTED`, `OUTCOME_UNKNOWN`, `REQUEUE_LIMIT_REACHED` or `CUSTOMER_HAS_NEWER_WORK`, and writes nothing. Repeating an applied decision with the same `If-Match` returns the item again without a second change or audit row, so a retried request is idempotent. That holds only while the item still shows the decision (open after a requeue, completed after a resolve); once it has been worked and exhausted again, the old version is `STALE_VERSION`. The requeue update itself matches only a safe failure. The schema does not tie `last_recovery_action` to the failure, because a requeued item's later attempts may still end with `OUTCOME_UNKNOWN` or `LEASE_EXPIRED`, and that item then needs a `RESOLVE` like any other.
7. **No retry once an effect may have begun.** A handler calls `Lease.beginEffect()` immediately before the first operation that may cause an external effect. The call durably records the attempt as `effect_attempt` in the same fenced, lease-checked way as a renewal, and a stale claim gets `false` and must cause no effect. From then on the attempt is never retried. A `Transient` or `Permanent` result is recorded as an unknown outcome, and `fail` matches nothing for it. The ledger enforces this from the row's own marker, not from the caller: `requireRecovery` (the `exhaust` update) records `OUTCOME_UNKNOWN` for a marked attempt whatever failure it is given, and `requeue` refuses a marked attempt even if its row records a safe failure. A `DEPENDENCY_UNAVAILABLE` reported after `beginEffect` is recorded as an unknown outcome, but it still releases the rest of the batch untried, as decision 2 does. If no outcome is recorded at all (a crash, a database outage, a failed recovery write, a handler `Error`), the expired lease does not let another instance claim the item: the next claim exhausts it as `OUTCOME_UNKNOWN`, whatever attempts remain, so it holds back its customer until a member's `RESOLVE`. Attempts that never called `beginEffect` keep the A2 takeover and retry. No effectful handler exists yet; every future one must call `beginEffect` before its first effect.
8. **A record, not an action.** Processing and recovery schedule nothing, approve nothing and send nothing. A4 composes `FollowUpWorkProcessor.process` into its scheduler, disabled by default, with its own bounded tenant rotation and shutdown.

## Consequences

- An outage costs no attempts while B1 reports it. Until an adapter connects ADR 0038's provider health to `FollowUpProviderHealth`, every batch is a single probe claim. This is safe but slow, and it is intended until A4 enables the scheduler with B1 in place.
- Each takeover after a crash still consumes an attempt (ADR 0037). A crash on the last attempt needs a member's `RESOLVE`, because the ledger cannot know whether the crashed holder acted.
- If an outcome write fails after the handler acted (for example, the database is unreachable), decision 7 keeps another instance from running the handler again, provided the handler called `beginEffect` first. An effect started before `beginEffect` breaks that guarantee, so handler reviews must check the call. If `beginEffect` itself cannot be written, the handler must not act.
- A requeue of an item that a newer cycle has already superseded, whether that cycle is still open or already finished, is refused with `CUSTOMER_HAS_NEWER_WORK`. The member resolves the item instead. The requeue's update reads its statement snapshot, so after it a second statement re-reads the customer's items with a fresh snapshot, and a newer item found then rolls the requeue and its audit row back with the same refusal. A newer item enqueued after that read has to insert an open row, which waits on the requeued item through the unique index on open items, so it can no longer supersede the requeue unseen.
- The backoff uses the absolute attempt number, so a requeued item starts near the cap. Requeues are rare, operator-driven and bounded.
- Counts by state, oldest due age and metrics remain with B3 ([#462](https://github.com/stevdrey/dokene/issues/462)), and the dashboard remains with B4 ([#464](https://github.com/stevdrey/dokene/issues/464)). The recovery list is a bounded operator read, not a metric.
- A release that does not know the two new audit event types cannot read a page that contains them (ADR 0006). Rollback is safe before the first recovery decision; after it, only roll forward.

## Composed by ADR 0040

[ADR 0040](0040-recurring-follow-up-scheduler.md) runs `FollowUpWorkProcessor.process` from a recurring scheduler that is disabled by default. It adds a budget admission port in front of each batch and supplies the Phase 4 handler, which only records the cycle and never calls `beginEffect`. Provider health still reads `UNKNOWN` until an adapter maps ADR 0038 onto `FollowUpProviderHealth`, and the scheduler stays disabled until that adapter exists.
