# Security Invariants

The following invariants are architectural requirements, not optional conventions.

1. No tenant-scoped data is accessed without an active tenant context.
2. Cross-tenant access must be blocked at both application and database layers.
3. LLM output never directly causes an external side effect.
4. Every outbound action is authorized, policy-checked, idempotent, and auditable.
5. Opt-out and consent restrictions always override automation.
6. Secrets never appear in source control, logs, prompts, or plaintext business tables.
7. External providers, webhooks, imported data, and user-generated content are untrusted.
8. Human approval is the default for outbound messaging until a tenant explicitly enables an allowed automation policy.
9. Security-sensitive state transitions are explicit and validated.
10. Runtime database credentials must not have schema-migration or RLS-bypass privileges, and the long-running backend never holds the migration credential: migrations run in a separate one-shot job, and the backend only validates the schema (issue 308, ADR 0003). The runtime role never deletes a tenant or a membership and may update only the columns ADR 0003 lists for them (tenant `display_name`, `status`, `updated_at`, `version`; membership `role`, `status`, `updated_at`, `version`); a membership's tenant and identity are fixed at insert (issues 183 and 315).

11. Runtime audit history is append-only; tenant reads require `AUDIT_READ` and signed-capability RLS. Audit rows cannot be updated, deleted or truncated by any role except through the documented owner break-glass (ADR 0006, issue 308).
12. Successful security-sensitive database transitions commit atomically with audit records; denied actions require independent durable auditing. Audit persistence failures abort the operation explicitly. AI invocation outcomes (generated, refused, gate-rejected, failed) are audited with closed metadata only.
13. Audit attribution comes from trusted execution context, and metadata accepts only closed, privacy-reviewed types. Unattributed global denials remain unreadable to the runtime role.
14. OIDC identities are linked only by a validated issuer and subject pair; email and provider role claims never establish identity linkage, membership, tenant context, or authorization.
15. Provider tokens remain server-side under the Backend for Frontend (BFF) architecture. The browser interacts solely through expiring, invalidatable application sessions with secure cookie semantics (`HttpOnly`, `SameSite=Lax`, `Secure`), session fixation rotation, and CSRF protection. Sessions end at an absolute lifetime regardless of activity, are invalidated by provider back-channel logout, and are revalidated against the provider at a bounded interval so that a disabled or logged-out provider user is denied within a documented bound (ADR 0007). Local logout invalidates the application session; provider logout redirects to the provider's end_session_endpoint with server-managed ID token hints without exposing tokens to the client. Forwarded header trust defaults to none and must be explicitly configured only behind trusted edge proxies that sanitize incoming proxy headers. Provider tokens and client secrets are never exposed to browser storage, JavaScript, error payloads, or logs.
16. Customer phone identity is normalized with explicit country context and unique within a tenant across active and archived history; customer mutations are authorized, RLS-protected, and audited without customer content.
17. Contact consent is channel- and contact-identity-specific, unknown consent fails closed, and customer do-not-contact overrides every grant. Consent evidence uses server time and trusted actor attribution; changing contact identity never transfers consent.
18. Purchase history is tenant/customer consistent and never physically deleted by the runtime; corrections and voids are versioned, traceable, and audited without purchase descriptions. Last purchase is derived only from valid history.
19. Follow-up eligibility is deterministic and tenant-local; archive, do-not-contact, and missing granted consent are hard constraints that cadence, manual state, AI output, and automation cannot override.
20. Due follow-up queue and operator dispositions (snooze, dismissal, manual completion) re-evaluate eligibility at execution time; revoked consent, customer archival, and do-not-contact fail dispositions with 409 Conflict. Free-form operator notes remain strictly outside audit log payloads. Changing the tenant-wide follow-up policy is tenant configuration, not a disposition, and needs `TENANT_UPDATE` ([ADR 0005](../adr/0005-tenant-aware-authorization.md)).
21. AI recommendations and drafts must pass through the deterministic AI Action Gate at evaluation time before acceptance or exposure; model output cannot override tenant authority, customer active status, consent, or deterministic follow-up eligibility. Stale or disallowed recommendations fail closed with typed rejection reasons and privacy-safe observability without customer PII or prompt text. Provider failures are normalized to stable categories before crossing the HTTP/UI boundary; retries are bounded, limited to transient side-effect-free generation and cannot bypass authorization or the gate; logs, metrics and audit never contain API keys, raw prompts, customer notes, phone numbers or generated message bodies, and metric tags never include tenant, customer, actor or correlation identifiers ([ADR 0019](../adr/0019-ai-failure-handling-telemetry-and-audit.md)).
22. The operator UI treats AI output as advisory, untrusted text: it is rendered as plain text, kept only in component state scoped to one customer and one workspace (discarded and aborted on selection or workspace change), never displayed unless the response carries a strong numeric ETag and names the requested customer, never reused once the follow-up policy version changed, and never offers an approve/send path before the Phase 3 message state machine exists. The browser calls only Dokene APIs and holds no provider credentials; hiding AI controls is a usability aid, not an authorization boundary ([ADR 0020](../adr/0020-frontend-ai-assistance-panel.md)). As defense in depth, SPA and BFF responses carry a restrictive Content-Security-Policy (no inline or third-party scripts/styles, no framing) and a Permissions-Policy ([ADR 0023](../adr/0023-spa-and-bff-response-security-headers.md)).
23. AI evaluation uses only invented synthetic data in isolated synthetic tenants and never real customer data or production prompts; live-provider evaluation is opt-in, needs explicitly supplied local credentials, is excluded from normal CI, and evaluation results never trigger a production rollout. Hard policy/security invariants are pass/fail and are never traded against language-quality scores ([ADR 0021](../adr/0021-ai-evaluation-harness-and-quality-baseline.md)).
24. Outbound messages exist only through the `OutboundMessage` aggregate: every state change is one of the sixteen ADR 0023 transitions, advances the message version by one and appends one event row; the transitions ADR 0023 §4.5 names commit their audit record in that same transaction (T7, the attempt claim, and non applied delivery reports write an event row and no audit row). At most one open message per customer per tenant is enforced by a database index, never only by application checks; open means `PENDING_APPROVAL`, `APPROVED`, `QUEUED` or `SENDING` (an unknown outcome included), so no provider call is made while another message to the customer waits for or is inside one, and `SENT` or `DELIVERED` messages do not block a new message (ADR 0023 §2, amended for [#198](https://github.com/stevdrey/dokene/issues/198)). Contact frequency after a send is guarded by the cadence anchor and the minimum contact interval, not by this index. Every operator command is authorized, is idempotent by `(tenant, operation, key)` with a payload fingerprint, and refuses a stale `If-Match` version without writing anything; submit, approve and send (T1, T2, T6) additionally re-check customer status, contact ownership, do-not-contact, consent and deterministic follow-up eligibility at execution time under the customer lock, while reject and cancel (T3 to T5) check only the message state and version by design. Customer follow-up policy writers take that same customer lock, so an evaluation a command made under the lock is still current when it commits. Provider delivery reports are applied only under a trusted provider context that names the tenant; the report payload never selects the tenant, a member context is refused, the provider attributed audit capability is signed only for the tenant that context names, and an out of order report is recorded as a non applied event rather than moving the message backwards. Message bodies, recipient phones, operator notes and provider message ids never appear in audit metadata or logs ([ADR 0023](../adr/0023-phase-3-outbound-messaging-contracts.md)). An approval binds the recipient, content, template mapping revision, exact template parameter values (rendered only from a closed vocabulary of stored fields, never from request or model text), sending identity and consent revision through the approval fingerprint, calls no provider, and is never edited: changing the text means cancelling and submitting a new message that needs its own approval; send recomputes it under the customer lock, refuses a mismatch with `APPROVAL_INVALIDATED` without writing anything, and sends exactly the bound parameter values. Secret values and raw provider JSON stay inside the `integration` module and never cross a messaging port, an HTTP response or audit metadata; only a `VerifiedWebhookEvent`, built after signature verification, stored-identifier tenant resolution and dedup, reaches the delivery sink, through a `VerifiedWebhookEventHandler` ([ADR 0024](../adr/0024-phase-3-messaging-contract-freeze.md)).
25. A provider phone number id is trusted for routing or sending only while its ownership is proven: the proof is made by the provider adapter with the owning tenant's own credential, never by the configuration API, and is cleared whenever the phone number id, business account or credential revision changes or the integration is disabled; the database rejects any write that would keep it. Only one tenant can hold a verified mapping of a number, an unverified claim never blocks the real owner, and tenant resolution without a tenant context goes only through the verified-mapping resolver, which returns a tenant id and nothing else ([ADR 0024](../adr/0024-phase-3-messaging-contract-freeze.md), issue 210).
26. Submit, approve, reject, cancel and send authorize against the membership as it is under the customer lock, not as the request resolved it, and audit a denial. A provider send happens only after one transaction has committed, under the customer and message locks, the full last-moment send policy, the T6 and T7 transitions and a `STARTED` attempt row naming the authorizing member. That row is the durable claim: at most one exists per message (database index), and while it or an unknown outcome is open no further send of the message can start. Any deterministic refusal writes nothing and makes no provider call. The provider is called outside any transaction and never retried automatically. If its outcome cannot be recorded, the claim is kept and sending halts rather than risk a duplicate; an expired claim may only become an unknown outcome for a human to resolve. A disable or revocation committed after the claim cannot retract a call already in flight. Application duplicate suppression is not proof of exactly-once delivery by the provider ([ADR 0028](../adr/0028-manual-dispatch-claim-and-last-moment-send-gate.md), issue 138).
27. A provider callback is trusted only after the HMAC over its raw bytes, a strict allowlist schema check (a member outside it refuses the body before any tenant lookup) and tenant resolution through the verified-mapping resolver. It is acknowledged only after every status is durably recorded in the tenant's RLS-protected inbox or deliberately dropped. Inbox rows hold typed delivery facts only, never raw provider JSON, error texts or recipient phones; they are deduplicated on `(provider, providerEventId)` and purged after a bounded retention. They are applied under a provider context with no member, in the same transaction as the transition and its audit. A report whose message is not found is parked for a bounded window and then dropped with its provider message id cleared, and a row that keeps failing is abandoned after a bounded window the same way. No webhook can create, approve or send a message ([ADR 0030](../adr/0030-verified-webhook-inbox-and-delivery-reconciliation.md), issue 139). The anonymous callback reads no body byte before its signature header, app secret reference and declared length pass, holds at most a configured number of bodies at once (excess requests get `503` unread), and throttles its refusal log lines (issue 306). The functions that read or purge across tenants for the inbox sweeper and dispatch recovery require a signed system-scoped `maintenance` capability, return ids only, and bound their cutoffs to the database clock: nothing not yet due or still in flight is listed, and nothing inside the minimum retention is purged (issue 313).
28. A membership grants access only while it is `ACTIVE`. An invitation stays `INVITED` until its own invitee accepts it through the identity-scoped acceptance, and a revoked membership returns only to `INVITED`, through an audited reactivation that requires `MEMBERSHIP_INVITE` and never applies to an owner. Ownership is never granted by an invitation, an acceptance or a reactivation ([ADR 0031](../adr/0031-membership-invitation-acceptance-and-audited-reactivation.md), issue 317).
29. Provider credentials and customer data are sent only to an allow-listed endpoint checked before any client is built: the Meta Graph API host or the OpenAI API host over HTTPS, a loopback test server (exact `localhost`, `127.0.0.1` or `[::1]` for OpenAI; the Graph policy still also accepts `*.localhost`, audit I3), or a host the deployment explicitly lists as trusted by exact host name (never an IP literal), never with user info, query or fragment in the URL; a rejected endpoint stops startup (ADR 0025, ADR 0016 §6, issue 322).
30. Inviting, reactivating, changing the role of and revoking a membership are decided against the actor's membership as it is in the writing transaction, after the tenant row is share-locked and the actor's and target's membership rows are locked in the request's tenant, not as the request resolved it. A refusal rolls back and is then audited ([ADR 0031](../adr/0031-membership-invitation-acceptance-and-audited-reactivation.md) §6, issue 325).
31. Every template parameter value and the rendered template body pass the message safety rules, with the same offer grounding and locale vocabulary as the body, whenever submit, review, approval or send renders a template. The only exemption is a closed list of real surnames, as the last word of the customer's exact capitalized name and never near a number, a written quantity or a claim word. An identity value is never grounded on a purchase. A refusal is the closed `BODY_REJECTED` before any provider call and never quotes a value ([ADR 0025](../adr/0025-whatsapp-template-registry-and-dispatch-policy.md), issue 326 addendum).
32. CI runs only reviewed third party code: every GitHub Actions reference outside this repository is pinned to a full 40 character commit SHA with the upstream release tag it was resolved from as the only comment beside it, one SHA per action repository across all workflows and local composite actions, and no workflow gains a permission to do so. Two layers hold the rule and neither replaces the other. `scripts/check-workflow-pins.sh` enforces the form on every pull request through `workflow-pins.yml`: the full SHA, the one token tag comment and one SHA per repository. It does not prove the SHA is the commit the named tag points at; that proof is the reviewer step with `git ls-remote` in the pinning page, made on every new or bumped pin. Dependabot keeps the pins current in one grouped weekly pull request after a seven day cooldown ([GitHub Actions pinning](github-actions-pinning.md), issue 309).
33. An anonymous request never creates a server session: a browser without a session gets one only from a login start (`GET /oauth2/authorization/{registrationId}`), the BFF chain stores no rejected request, and a CSRF token is stored only in a session that already exists. A session that has not completed login never idles longer than the pre login timeout and does not survive a request made after it is older than that; a signed in session always has the normal idle timeout. A failed login ends its login start session and never a signed in one. Login starts are limited per client address at the edge, and a refused one never reaches the backend ([ADR 0007](../adr/0007-oidc-server-side-session.md), issue 311).
34. Builds, tests and the local stack run only reviewed image content: every reference to a container image not built from this tree is `<name>:<tag>@sha256:<digest>` with the multi platform index digest, one digest per `name:tag` across all files, and no Java test or shell script names an image by a literal of its own (tests read PostgreSQL from `compose.yaml`). The Gradle Wrapper verifies its distribution against `distributionSha256Sum` before running it. `scripts/check-image-pins.sh` enforces the form and the checksum line on every pull request through the `image-pins` job of `workflow-pins.yml`; it does not prove a digest is the one its tag pointed at, which is the reviewer step in the pinning page. Dependabot keeps the pins current in grouped weekly pull requests after a seven day cooldown and never proposes a major version. Gradle dependency verification and the Testcontainers `ryuk` helper image are deferred there in writing ([Build input pinning](build-input-pinning.md), issue 323).
35. A credential never travels on a process command line, which any local user can read in the process table. The local setup, seed and verification scripts in this repository hand a password, key, secret, bearer token, session cookie, CSRF token or OAuth authorization code to a tool through that one command's environment (`VAR=value tool`, `docker compose exec -e VAR` by name, `KC_CLI_PASSWORD` for `kcadm.sh`, `\getenv` in `psql`), its standard input (`curl --data-urlencode "password@-"`, `--data-binary @-`), or a file descriptor (`curl -H @<(…)`, `grep -F -f <(…)`), never as an argument. Generated values are written byte for byte, escapes included, and a failure message names a secret, never prints it. Scripts search logs and responses for secrets with `scripts/lib/secret-match.sh`, which keeps the values off grep's command line. Scripts that call the BFF load `scripts/lib/curl-protected.sh` (directly or through `scripts/lib/bff-login.sh`), which hands curl every header, cookie value and URL in a `-K` config on a file descriptor. Historical evidence scripts under `docs/verification/` that record past runs are the one known exception until [#401](https://github.com/stevdrey/dokene/issues/401) brings them in line; they run only on demand against a disposable local stack with synthetic data, and no new script may be added in that form. The residual exposure is the environment of the one process that needs the value, readable only by its own user and root (issue 327).
36. The nginx edge sends the backend no client supplied forwarding header. It sets `X-Forwarded-For` to its peer, or to the client address restored from a proxy listed in `trusted-proxies.conf`, `X-Forwarded-Proto` to its own scheme, and `X-Forwarded-Port` to the port of the pinned `Host`. The backend may use `framework` only for traffic through this edge ([ADR 0007](../adr/0007-oidc-server-side-session.md), issue 320).
